# Строгая проверка решения перед сдачей

Этот документ описывает критерии приемки и методологические ограничения. Это не отчет об успешном выполнении всех проверок: фактические результаты запуска нужно смотреть в отчетах проекта. Точные реализованные формулы и пороги задаются кодом, конфигурацией и `METHODS.md`.

## Основание и текущие границы

Источник требований: предоставленный PDF «HackAlem AI: Граф денег: восстановление финансовой структуры организованной группы по транзакционной сети».

На момент подготовки проекта доступны условия кейса, но не оригинальные `nodes.parquet`, `edges.parquet`, `transactions.parquet` и README датасета. Поэтому проект нельзя представлять как уже рассчитанное расследование этой сети. Демонстрационные данные должны быть явно обозначены как синтетические. Никакие их `gid`, роли, суммы или показатели скорости не являются результатами анализа исходного датасета.

В условиях нет размеченных ролей. Нельзя сообщать accuracy, precision, recall относительно истинных ролей, процент найденных организаторов или вероятность виновности. Можно измерять корректность преобразования данных, воспроизводимость, время расчета, выполнение формальных правил и чувствительность к выбранным сценариям.

Первые три критерия дают 75 из 100 баллов. Дополнительные функции не должны ставить под угрозу обязательный локальный расчет.

## Обязательный контракт

- Один запуск обрабатывает три исходных `.parquet` и создает три обязательных CSV без ручного исправления промежуточных результатов.
- `nodes_roles.csv`: `gid, role, role_score, cluster_id, priority_score, evidence`. Одна строка на каждый узел, включая изоляты. Роль из документированного словаря, оба скора конечны и находятся в [0, 1], explanation непустой и длиной не более 200 символов.
- `clusters.csv`: `cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis`.
- `top_nodes.csv`: `rank, gid, role, priority_score, why`. Для исходного кейса не менее 20 узлов, сортировка по приоритету с детерминированным разрешением равенств. Для малых тестовых наборов допустимо вывести все доступные узлы.
- Интерфейс показывает направленные связи, роли, кластеры и поиск по `gid`. Узел без рёбер тоже находится.
- Полный пересчет исходного объема выполняется локально не более чем за пять минут. Время подтверждается измерением, а не обещанием.
- README описывает команду запуска, зависимости, правила, ограничения и изменения архитектуры при росте до примерно миллиона узлов.

Указанные в PDF размеры и счетчики используются для сверки, а не для зашитых ответов. В PDF есть арифметическое несоответствие: 2248 - 1877 = 371, тогда как вне крупнейшей компоненты указано 352; разница равна 19 заявленным изолированным seed. Фактические размеры и состав компонент нужно вычислить по данным и сохранить в отчете.

## Границы интерпретации

### Роли и скоры

Роль — структурная гипотеза для проверки. `role_score` означает силу документированного правила на наблюдаемом срезе, а не калиброванную вероятность истинности роли. `priority_score` — порядок аналитической проверки, а не уровень виновности.

Нельзя принуждать классификатор выдавать все шесть ролей, подбирать `gid` вручную или повышать роль до «организатора» по одной центральности. Для пересекающихся ролей полезно хранить альтернативные баллы в расширенной карточке. В обязательном CSV остается одна основная роль.

### Неполнота наблюдения

- Отсутствие исходящих у `depth=4` вызвано границей обхода. Такой факт не является основанием для `terminal`.
- У seed входящие потоки неполны. Отношение исходящих к входящим не должно самостоятельно определять их роль.
- Исходящие больше входящих не доказывают аномалию или появление денег. Возможны ненаблюдаемые поступления и начальные остатки.
- Для узла с `depth<4` отсутствие наблюдаемых исходящих поддерживает только гипотезу терминальности в данном срезе. Другие банки, переводы ниже порога и последующие периоды отсутствуют.
- Поступления в конце июля имеют короткое окно для наблюдения дальнейших переводов. Это отдельное ограничение временной проверки.
- Нельзя заключать, что невидимого дробления ниже 5000 KZT не существует. Датасет не позволяет проверить его напрямую.

### Пути, ветви и время

- Количество seed, от которых достижим узел, — охват исходных клиентов. Это не количество независимых финансовых источников.
- Разные непосредственные предшественники могут иметь общего предка. Называть пути независимыми можно только после соответствующей проверки непересечения.
- Циклический обход не должен повторно засчитывать один seed. Применяются visited-set или граф компонент сильной связности.
- Графовый путь не доказывает последовательное движение средств. Для временного маршрута нужен совместимый порядок исходных транзакций.
- Если имеется только дата, порядок двух переводов внутри одного дня неизвестен. Однодневная совместимость должна быть обозначена отдельно от строгой хронологии.
- Суммы нельзя повторно расходовать при построении совместимых входов и выходов. Совместимость сумм не устанавливает, что переведены те же самые деньги.
- Цикл в агрегированном графе — структурный цикл. Без временной проверки он не является установленным возвратом средств.

## Надежность входных данных

1. Сохранить `gid` как целое int64, не проводить его через float. В JavaScript безопаснее передавать идентификатор строкой: целые больше 2^53 теряют точность в обычном Number.
2. Проверить уникальность `nodes.gid` и наличие всех концов рёбер и транзакций в таблице узлов.
3. Явно нормализовать `is_seed`; строка `"False"` не должна превращаться в true.
4. Проверить даты, допустимость сумм и целочисленность счетчиков. Поврежденные строки не следует молча отбрасывать.
5. Агрегировать transactions по `(src, dst)` и сравнить суммы и количество с edges. Это два представления одних переводов; их обороты нельзя складывать.
6. Идентичные строки transactions без уникального идентификатора могут обозначать разные реальные операции. Их нельзя автоматически удалять как дубли.
7. Внутренний оборот кластера считать по каждому направленному внутреннему ребру ровно один раз.
8. Самопереводы и отсутствующие данные обрабатывать явным правилом с отражением в отчете.
9. В кратчайших путях `sum_kzt` не является расстоянием. Для MVP подходит невзвешенная betweenness; иное преобразование веса необходимо объяснить.
10. Нумерация кластеров, сортировка равных скоров и случайное начальное состояние алгоритмов должны быть детерминированными.

## Минимальный набор содержательных тестов

Эти сценарии задают приемку. Наличие пункта в списке не означает, что он уже реализован в тестовом наборе.

| Сценарий | Ожидаемое поведение |
|---|---|
| Узел depth=4 без исходящих | Не становится `terminal` из-за отсутствия исходящих |
| Seed с ненаблюдаемым входом | Балансовое отношение не дает ложного уверенного заключения |
| Изолированный seed | Сохраняется во всех соответствующих результатах и находится в интерфейсе |
| Цикл с одним исходным seed | Охват seed не растет из-за повторного обхода |
| Переводы одной даты | Не возникает утверждения об известном порядке внутри дня |
| Структурный цикл с несовместимыми датами | Не объявляется доказанным временным возвратом |
| Законные одинаковые транзакционные строки | Не теряются при загрузке |
| Edges не совпадает с агрегатом transactions | Понятная ошибка или явный отчет согласно задокументированной политике |
| `gid` больше 2^53 | Идентификатор не меняется при экспорте и поиске |
| Повторный запуск | Совпадают CSV при одинаковом вводе и конфигурации |
| Изменение входного перевода | Пересчитываются соответствующие метрики и объяснения |
| Полный smoke-run | Появляются все обязательные CSV и интерфейс |

## Как проверять дополнительные идеи

- **Устойчивость:** доля сценариев, в которых узел сохраняет роль или место в топе, относится только к явно указанному набору изменений порогов. Это не доверительная вероятность.
- **Следующий запрос:** полезность запроса до получения ответа — объяснимая оценка, не доказанный ожидаемый эффект.
- **Эксперимент со скрытыми данными:** сначала скрыть часть наблюдаемой сети, затем рассчитывать стратегию только на доступной части. Раскрывать скрытые сведения исключительно по выбранным запросам. Сравнивать с простыми стратегиями при одинаковом бюджете.
- **Метрика такого эксперимента:** восстановление заранее определенных наблюдаемых свойств или ранжирования полной доступной сети. Это не доказательство распознавания истинных ролей или качества за пределами банка.
- **Симуляция удаления узлов:** изменение связности наблюдаемого графа. Не выдавать его за прогноз эффекта реальной блокировки счетов или за причинную модель поведения группы.

## Что нужно сделать при получении архива

Сверить схему с README датасета, выполнить валидацию, проверить охват всех узлов, запустить пайплайн, измерить время и вручную разобрать несколько seed, пограничных узлов, изолятов и кандидатов разных ролей. После этого сохранить отчет с фактическими счетчиками. Только такой запуск позволяет заявить о готовности на данных кейса.
